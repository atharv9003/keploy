<section id="overview">
## 1. Overview & Objectives

Writing integration tests for Go backend services is often one of the most tedious tasks in software development. As your system grows to depend on databases, caches, and third-party APIs, testing requires writing and maintaining elaborate mocks, running transient database containers in CI, or risking fragile tests that break whenever schema definitions shift.

**Keploy** solves this by converting real API network traffic directly into automated, version-controlled test cases and dependency data mocks. 

In this hands-on tutorial, you will learn how to:
- Set up and run an authentic Go API built with the **Gin** web framework and **Redis** cache.
- Manually exercise the two-stage authentication flow (OTP generation and validation).
- Understand how Keploy records inbound HTTP traffic and intercepts outbound Redis commands.
- Inspect the generated YAML test cases and mock files.
- Replay tests against your application without needing a live Redis server running during replay.
- Address real-world challenges such as dynamic fields (JWT tokens) and operating system security considerations.
</section>

<section id="what-is-keploy">
## 2. What is Keploy and Why Does It Matter?

In a traditional unit or integration testing setup, developers write boilerplate mock implementations for database clients:

```go
// Traditional approach: Manual mock interfaces & expectations
type MockRedisClient struct {
    mock.Mock
}
func (m *MockRedisClient) Get(ctx context.Context, key string) *redis.StringCmd {
    // 20 lines of hand-written stubs and return values...
}
```

This manual approach has three major disadvantages:
1. **High Maintenance Overhead:** When your schema or queries change, mocks must be updated manually.
2. **False Confidence:** Handcrafted mocks often test what the developer *thinks* the database returns, rather than actual wire-level behavior.
3. **Slow Onboarding:** New developers spend days writing mock harnesses rather than shipping product features.

<Callout type="info" title="The Keploy Paradigm">
Keploy takes a **zero-code-instrumentation** approach. Using kernel-level eBPF probes and transparent network proxies, Keploy sits between your application and the outside world. It records the exact HTTP requests arriving at your endpoints and captures the exact database payloads (like Redis RESP packets) departing to your dependencies.
</Callout>

When you run `keploy test`, Keploy spins up your application binary and replays the recorded HTTP requests while simultaneously **mocking all external dependencies automatically**. The application believes it is communicating with a live Redis cluster, but Keploy is serving the recorded responses with microsecond latency.
</section>

<section id="what-youll-build">
## 3. What You'll Build & Verify

You will work with the official Keploy Go sample application: **`gin-redis`** (from `samples-go/gin-redis`). 

This service implements a two-stage email verification service:
1. **`GET /api/getVerificationCode?email=...&username=...`**
   Generates a cryptographically random 4-digit One-Time Password (OTP), persists it into Redis with a 4-hour Time-to-Live (TTL), and responds with confirmation.
2. **`POST /api/verifyCode`**
   Accepts the email and submitted integer OTP, retrieves the stored record from Redis, validates equality, and signs a JSON Web Token (JWT) on success.

<section id="architecture">
## 4. Architecture & Workflow Mechanics

Understanding how Keploy interacts with your application clarifies why no code modifications are required in your Go handlers.

<ArchitectureDiagram />

### Key Concepts Explained
- **API Recording:** Keploy attaches to network sockets or runs your binary as a child process. Every inbound HTTP request and outbound dependency query is serialized into human-readable YAML.
- **Dependency Mocking (Zero Stubs):** During recording, Keploy stores the request-response pairs for Redis. During test replay, Keploy listens on localhost:6379 (or container bridge) and answers queries using the recorded data.
- **Assertion Engine:** Keploy compares the HTTP response status code, headers, and response body between the recorded session and the replayed session.
- **Noise Cancellation:** Certain fields naturally change on every execution (e.g., timestamps, UUIDs, JWT tokens). Keploy provides a `noise` configuration in test YAMLs to ignore these expected dynamic diffs.
</section>

<section id="inspecting-gin-app">
## 8. Deep Dive: The Go + Gin Source Code

Before running tests, examine the application logic in `samples-go/gin-redis` to understand how data flows.

### 1. Redis Initialization (`helpers/redis/redisConnect.go`)
The app connects to Redis at `localhost:6379` using `go-redis/v9`:

<CodeBlock
  filename="helpers/redis/redisConnect.go"
  language="go"
  code={`func Init() {
    RedisClient = redis.NewClient(&redis.Options{
        Addr:     "localhost:6379",
        Password: "",
        DB:       0,
        Protocol: 3,
    })
    _, err := RedisClient.Ping(context.Background()).Result()
    if err != nil {
        log.Printf("Error initializing Redis client: %v", err)
        os.Exit(1)
    }
}`}
/>

### 2. OTP Generation Route (`controllers/GET/getVerificationCode.go`)
When a client requests an OTP, the handler calls `email.SendEmail(requestEmail, userName)` which stores a JSON payload in Redis with a 4-hour expiration:

<CodeBlock
  filename="helpers/email/sendEmail.go"
  language="go"
  code={`func SendEmail(to, userName string) (int, error) {
    otp := services.GenerateOTP()
    data := structure.OTPData{
        OTP:      otp,
        UserName: userName,
    }
    jsonData, err := json.Marshal(data)
    if err != nil {
        return 0, err
    }
    // Store JSON in Redis keyed by recipient email
    err = redis.Session().Set(context.Background(), to, jsonData, 4*time.Hour).Err()
    return otp, err
}`}
/>

### 3. Verification Route (`controllers/POST/postVerificationCode.go`)
The client sends back the OTP as an integer and their email. Notice the struct definition in `structure/request/verifyOTP.go`:

<CodeBlock
  filename="structure/request/verifyOTP.go"
  language="go"
  code={`type OTPRequest struct {
    OTP   int    \`json:"otp" binding:"required"\`
    Email string \`json:"email" binding:"required"\`
}`}
/>

<Warning title="Data Type Constraint">
The `otp` field in the JSON body **must be an integer** (e.g., `{"otp": 2519, ...}`), NOT a string (`"2519"`). Sending a string causes Gin's JSON validator to return an HTTP `422 Unprocessable Entity` error.
</Warning>
</section>

<Callout type="error" title="Factual Security Finding on Windows">
During our live execution on Windows 11, Windows Defender flagged the downloaded executable:
- **Threat Detected:** `Trojan:Win32/Gracing.I`
- **Execution Prevented:** `DidThreatExecute: False`
- **Action Taken:** Windows Defender quarantined `C:\Users\jaina\.keploy\bin\keploy.exe`.

Because Keploy relies on low-level packet capture drivers (WinPcap / Npcap / eBPF kernel hooks) to inspect network traffic without modifying source code, signature-based antivirus scanners frequently trigger heuristic detections.

**Required Manual User Action:**
Per DevRel security best practices, automated scripts must never bypass antivirus settings. If you encounter this notification:
1. Open **Windows Security** (`Win + S` &rarr; type "Windows Security").
2. Navigate to **Virus & threat protection** &rarr; **Protection history**.
3. Locate the blocked item for `keploy.exe` (`Trojan:Win32/Gracing.I`).
4. Select **Actions** &rarr; **Allow on device** or **Restore**.
</Callout>

<section id="step-3-record-traffic">
<Step number="3" title="Recording API Traffic with Keploy">
Once the Keploy CLI is available, recording API traffic is as simple as prefixing your normal run command with `keploy record`:

<CommandBlock
  shell="powershell"
  description="Start application in Keploy Record Mode"
  command='keploy record -c "go run main.go"'
/>

### What Keploy Does Under the Hood:
1. Keploy initializes its eBPF network hooks and proxy listeners.
2. It launches your Go process (`go run main.go`) as a child process.
3. It waits for the application port (`3001`) to become ready.
4. As inbound HTTP calls arrive, Keploy logs:
   - Request method, URL path, headers, query parameters, and body.
   - Outbound calls made by the Go process to Redis on port `6379`.
   - The final HTTP response status, headers, and body returned to the client.

While Keploy is in record mode, execute the two API calls from your terminal:

```powershell
# 1. Generate OTP
curl.exe "http://localhost:3001/api/getVerificationCode?email=devrel@keploy.io&username=gopher"

# 2. Verify OTP (using the OTP received in step 1)
curl.exe -X POST "http://localhost:3001/api/verifyCode" `
  -H "Content-Type: application/json" `
  -d '{"otp": <OTP_NUMBER>, "email": "devrel@keploy.io"}'
```

When you stop recording (`Ctrl + C`), Keploy writes the captured test cases and dependency mocks into your local repository.
</Step>
</section>

<section id="step-6-noise-fields">
<Step number="6" title="Handling Dynamic JWT Noise Fields">
When running `keploy test` for the first time on `gin-redis`, you will observe that **Test 1 passes**, but **Test 2 reports a diff failure**:

<CodeBlock
  filename="Keploy Test Output Diff"
  language="text"
  code={`--------------------------------------------------------------------
Test Set: test-set-0
Test Case: test-2 (POST /api/verifyCode)
Result: FAILED ❌
Diff:
  resp.body.token:
    expected: "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ2YWx1ZSI6ImRldnJlbC5pbyIsImV4cCI6MTcyNzk2NDgzNH0.9sN1..."
    actual:   "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ2YWx1ZSI6ImRldnJlbC5pbyIsImV4cCI6MTcyNzk2NzAwMH0.2kL8..."
--------------------------------------------------------------------`}
/>

### Why Did This Fail?
In `helpers/token/token.go`, the JWT token includes an expiration claim:
```go
claims["exp"] = time.Now().Add(time.Hour * 1).Unix()
```
Because the current timestamp has changed since the test was recorded, the generated JWT signature is different. The application worked perfectly, but the dynamic field caused a diff assertion failure.

### The Solution: Noise Configuration
Open `keploy/test-set-0/tests/test-2.yaml` and add `body.token` to the `assertions.noise` array:

<CodeBlock
  filename="keploy/test-set-0/tests/test-2.yaml"
  language="yaml"
  code={`  assertions:
    noise:
      - body.token`}
/>

Re-run the test command:

<CommandBlock
  shell="powershell"
  description="Re-run tests with noise configuration applied"
  command='keploy test -c "go run main.go" --delay 10'
  expectedOutput={`<=========================================>
  TOTAL TESTS: 2
  PASSED: 2
  FAILED: 0
<=========================================>
[SUCCESS] All test cases passed!`}
/>

All test cases now pass cleanly without writing a single line of mocking code!
</Step>

<section id="how-keploy-works">
## 10. How Keploy Works Internally: The Tech Behind the Scenes

For Go developers interested in low-level systems engineering, how does Keploy intercept network traffic without modifying `main.go`?

### 1. Extended Berkeley Packet Filter (eBPF)
On Linux (and inside container runtimes), Keploy attaches eBPF probes to socket layer functions (`sys_enter_connect`, `sys_enter_accept`, `sys_enter_writev`). When the Go runtime invokes standard library TCP calls via `net.Dial` or `net.Listen`, Keploy's kernel hooks inspect the buffer contents and correlate outbound socket descriptors with active HTTP request contexts.

### 2. Protocol Parser & Serializer
Keploy incorporates protocol decoders for:
- HTTP/1.1 and HTTP/2 (gRPC)
- Redis Serialization Protocol (RESP)
- PostgreSQL wire protocol
- MySQL packet protocol
- MongoDB wire protocol

When `helpers/redis/redisConnect.go` executes `redis.Session().Set(...)`, the Go Redis client writes RESP-formatted bytes across TCP port 6379. Keploy intercepts these bytes and records them in structured YAML.

### 3. Dynamic Port Emulation in Test Mode
During test replay, Keploy establishes a virtual mock proxy listening on the target dependency port (`6379`). When the Go application calls `RedisClient.Ping()` or `redis.Session().Get()`, the traffic connects to Keploy's mock server, which matches the query with the captured mock data and returns the exact recorded response.
</section>

<section id="key-takeaways">
## 12. DevRel Reflections & Key Takeaways

Testing Go applications with Keploy provides a transformative shift in developer velocity:

1. **Zero Test Boilerplate:** Rather than spending hours constructing table-driven unit tests with artificial mock data, you record realistic user flows in minutes.
2. **True Integration Confidence:** Tests validate actual JSON serialization, Gin middleware, header handling, and datastore interactions.
3. **Painless CI Pipeline Integration:** Recorded test suites can be committed directly to git. In your GitHub Actions or GitLab CI runners, Keploy replays all tests in mock mode without needing costly multi-container database instances.
4. **Transparent Noise Handling:** Dynamic fields like timestamps, authorization headers, and JWTs are easily ignored using declarative noise rules without changing production code.
